# ADR-0003: 地域パッケージを 2 次メッシュ単位で分割し、道路グラフを SQLite 形式で配布する

- ステータス: Accepted
- 日付: 2026-07-18
- プロジェクト: tendenko

## コンテキスト

データパイプライン (pipeline/) が生成する地域パッケージについて、(1) 地域分割の単位と (2) 道路グラフのフォーマットを決める必要がある。制約は要件定義書から:

- FR-02/03: ローリングキャッシュ — 現在地周辺の自動 DL と、significant location change での移動先先読み。分割単位は移動に追従して数個ずつ落とせる粒度が必要
- FR-04: 全国分の最小データセット (浸水想定ポリゴン + 避難場所座標 + 粗密度 DEM) < 50MB を同梱
- FR-12: 経路コストは浸水リスク・標高勾配・曲がり回数を重み付けする**カスタムコスト関数**。重みはチューニング対象であり、**探索時に端末側で動的に計算する**
- FR-15: 詳細データ未取得地域は縮退モード (コンパス案内) で成立する
- NFR-03: コールドスタートで現在地から経路確定まで < 5 秒 (端末内計算)
- NFR-04: 1 地域パッケージ < 150MB / 同梱最小データセット < 50MB
- 要件 §6: 端末ストレージ層は GRDB (SQLite) / MBTiles を想定済み

FR-12 の帰結として、**コスト関数を前処理で焼き込む方式 (OSRM の Contraction Hierarchies 等) は前提から不適合**。グラフは生の隣接構造 + 静的属性で持ち、コストは探索時に計算する。

## 決定

### 1. 分割単位: 2 次メッシュ (JIS X 0410、約 10km 四方)

- メッシュコード (例: `5339-24`) をパッケージ ID とする。緯度経度から機械的に算出でき、境界ポリゴンデータが不要
- **フルパッケージを生成するのは沿岸メッシュのみ** — 津波浸水想定区域と交差するメッシュ + 海岸線から一定バッファ内のメッシュ (閾値はパイプライン実装時に実測して決める)。内陸は同梱最小データセット + 縮退モード (FR-15) で成立する
- ローリングキャッシュは現在地メッシュ + 周囲 8 メッシュ (3×3) を保持。登録地点 (FR-05) も同様に 3×3 で常時保持
- パッケージ一覧・バージョン・ハッシュ・生成日時は manifest (JSON) で GCS に置き、FR-06 の差分 DL と「6 ヶ月超は警告」(要件 §8) の判定に使う

### 2. 道路グラフ: SQLite (1 メッシュ 1 ファイル) + 端末でメモリ展開

パイプライン (Go) が `region-<meshcode>.sqlite` を生成する:

| テーブル | 内容 |
|---|---|
| `nodes` | id (OSM 由来のグローバル ID), lat, lon, 標高 (DEM から焼き込み) |
| `edges` | from, to, 距離, 標高勾配, 方位角, 属性フラグ (浸水想定区域内・階段・私道・橋 等) |
| `shelters` | 指定緊急避難場所 (災害種別: 津波) の座標・名称・標高 |
| `meta` | メッシュコード, 生成日時, ソースデータのバージョン, スキーマバージョン |

- 静的属性 (浸水ポリゴンとの交差判定、DEM との結合) は**パイプライン側で焼き込む**。端末は幾何演算をしない
- 端末 (Swift) は GRDB で読み込み、現在地周辺メッシュ (3×3) の隣接リストをメモリ展開してドメイン層の A* に渡す。コスト関数は探索時に属性から動的計算 — ドメイン層は「展開済みグラフ → 経路」の純粋関数として TDD できる
- メッシュ跨ぎ: エッジは始点ノードが属するメッシュに収載する。ノード ID がグローバルなので、3×3 の読込結果を単純結合すれば境界を跨ぐグラフになる
- 地図タイルは同じメッシュ単位の MBTiles (tilemaker 生成)。パッケージ = `region-<meshcode>.sqlite` + `tiles-<meshcode>.mbtiles`

## 検討した選択肢

### 分割単位

**市区町村** — ✅ 避難場所データ (自治体単位で整備) と整合し人間に分かりやすい。❌ 境界ポリゴンが必要で合併により変化する。面積のばらつきが極端 (数 km² 〜 1,500km² 超) で、NFR-04 を分割単位側で保証できず、大きい市は結局内部分割する二重構造になる。**棄却**

**1 次メッシュ (約 80km 四方)** — ✅ パッケージ数が少なく管理が楽。❌ 都市部で道路グラフ + 地図タイルが 150MB をほぼ確実に超過し NFR-04 と衝突。先読みの 1 単位も重い。**棄却**

**3 次メッシュ (約 1km 四方) / 可変クアッドツリー** — ❌ 3 次は粒度過剰でパッケージ数とリクエスト数が爆発する。可変分割はサイズ効率が最良だが、分割ロジック自体が保守対象になり個人開発の運用時間と相性が悪い。**棄却** (都市部の 2 次メッシュが 150MB を超える事態が実測で判明したら再検討)

### 道路グラフフォーマット

**自前バイナリ (FlatBuffers 等の mmap 形式)** — ✅ 読込は最速。❌ スキーマ進化・破損調査・中身確認のツールをすべて自作し、Go (書き手) と Swift (読み手) の両方で保守する。NFR-03 の 5 秒は SQLite でも余裕で満たせる見込みのため過剰最適化。**棄却** (実測で SQLite が 5 秒を脅かす場合のみ再検討)

**Valhalla タイル** — ✅ 実績あるエンジンで動的コスティング機構もある。❌ C++ ライブラリの iOS 組み込みが重く、浸水リスク × 標高勾配の独自コストはエンジン内部への改修が必要。ドメイン層を純粋 Swift + TDD で書く方針 (CLAUDE.md) と衝突。**棄却**

**OSRM / Contraction Hierarchies 系** — ❌ コスト関数を前処理で焼き込む前提が FR-12 (動的コスト) と根本的に不適合。**即棄却**

## 正直な弱点

- **SQLite 読込 + メモリ展開のコールドスタート性能は未実測**。NFR-03 (5 秒) に対し、app 側の実装初期にベンチマークを書いて検証する。超過する場合は展開範囲の縮小 (3×3 → 現在地 + 進行方向のみ) から先に試す
- 都市部 2 次メッシュのパッケージサイズも未実測。パイプラインの垂直スライス実装で最初に確認する
- 沿岸メッシュは千数百個規模になる見込みで、manifest と GCS レイアウトの設計が必要 (パイプライン実装時)
- 道路グラフは OSM の派生データベースであり、**公開配布時の ODbL share-alike 義務の整理が未決のまま残る** — [ADR-0002](0002-oss-licensing.md) / [docs/licenses.md](../licenses.md) で追跡

## 検証記録 (2026-07-18 垂直スライス実測)

実在の 2 メッシュで region.sqlite を end-to-end 生成した (OSM 東北抽出版 + 地理院 DEM10B、pipeline/cmd/build-package)。

| メッシュ | 地域 | ノード | エッジ | region.sqlite | 生成時間* |
|---|---|---|---|---|---|
| 584177 | 釜石市中心部 (沿岸・地方) | 8,397 | 8,729 | **0.9 MB** | 3.5 秒 |
| 574036 | 仙台市中心部 (都市・高密度) | 61,198 | 70,061 | **7.4 MB** | 8.1 秒 |

*生成時間の大半は DEM タイル初回取得 (ネットワーク)。キャッシュ後は 1 秒未満。osmium のメッシュ切り出しは東北全域 291MB からで約 3 秒。

**結論: 道路グラフは NFR-04 (150MB) に対して支配項ではない** (都市部最悪級でも 1 桁 MB)。パッケージサイズの支配項は地図タイル (MBTiles) になる。

**未完了**: MBTiles の実測は nixpkgs の tilemaker 3.1.0 が macOS/arm64 でクラッシュするため保留。本番パイプラインは Cloud Run jobs (Linux) で動かすため、Linux 環境での実測が必要。浸水域フラグ (A40) と避難場所 (shelters) の取り込みも未実装。

### 追記 (2026-07-19): 東北全域の一括生成

海岸線からの沿岸メッシュ自動列挙 (バッファ 1 リング) + 一括生成を東北全域で実行した。

- 対象 489 メッシュ (海岸線 235 + バッファ) → **生成 309 パッケージ / スキップ 180 (海上等の空メッシュ)**
- 合計 **411MB**、中央値 1.1MB、最大 10.6MB (574037 = 仙台北東部)。**全メッシュが NFR-04 (150MB) に 1 桁以上の余裕**
- 所要 695 秒 (DEM 大半キャッシュ済み)。初回は DEM 取得律速で約 2 倍
- 教訓: 長時間バッチでは DEM タイル取得の一時的な connection reset が実際に発生する。指数バックオフのリトライ (4 回) を dem クライアントに実装済み

### 追記 (2026-07-20): 全国一括生成の実測

japan-latest.osm.pbf (2.3GB) から全国の沿岸パッケージを一括生成した。

- 海岸線メッシュ 1,806 + バッファ = 対象 4,481 メッシュ → **生成 2,515 パッケージ / スキップ 1,966 (海上等)**
- 合計 **4.55GB** (GCS 側の総量。端末が持つのは 3×3 + 登録地点のみ)、総ノード数 3,950 万
- 中央値 1.1MB、**最大 26.5MB (533946 = 東京都心)**。全パッケージが同梱最小データセット制約 (50MB) すら下回り、**NFR-04 (150MB) は全国で成立**
- 所要 2.6 時間 (DEM 初回取得が律速。タイルキャッシュ済みなら大幅短縮)
- 教訓: 4,481 メッシュの直接 bbox 抽出は osmium が OOM kill される。1 次メッシュ (80km) 単位で
  20 個ずつ切り出してから配下の 2 次メッシュを展開する 2 段階方式で解決した

### 追記 (2026-07-19): 端末側読込 + 探索の実測 (NFR-03)

GraphLoader (GRDB) + EvacuationRouter (ターン抑制付き Dijkstra、動的コスト) を実装し、実パッケージで計測 (macOS, arm64):

| パッケージ | ノード | 読込 | 探索 (最遠点) |
|---|---|---|---|
| 釜石 584177 (0.9MB) | 8,397 | 0.03 秒 | 0.004 秒 |
| 仙台北東 574037 (10.6MB, 最大) | 85,492 | 0.33 秒 | 0.49 秒 |

**「SQLite + メモリ展開」で NFR-03 (< 5 秒) に 1 桁の余裕**があり、自前バイナリ形式の再検討は不要と判断。実機 (iPhone) と 3×3 結合での再計測は app 実装時に行う。

### 追記 (2026-07-20): 浸水想定区域フラグ・避難場所テーブルの実装

FlagInundation の付与と shelters テーブルの実装を行った。実データ (国土数値情報 A40・国土地理院の指定緊急避難場所) の**取得元 URL はまだ確認していない** — ダウンロード URL を推測で使わない方針のため、次のいずれかをユーザーに確認してから着手する: (a) 具体的な配布 URL、(b) 既にローカルにある元データファイル。

そこで pipeline は**正規化 GeoJSON を受け取る形**で実装した。実データ取得後は ogr2ogr 等で以下の形式に変換するだけで使える。

- `internal/inundation`: Polygon/MultiPolygon の FeatureCollection (座標は GeoJSON 標準の `[lon, lat]`)。穴 (内水面など) は内側リングとして表現でき、外周とのレイキャストを XOR することで正しく除外する
- `internal/shelterdata`: Point の FeatureCollection、`properties.tsunami == true` の地物のみ採用 (FR-04 の「災害種別: 津波」)。`properties.name` を避難場所名とする

`build-package` に `-inundation <path>` `-shelters <path>` を追加 (両方省略可。省略時は従来どおり FlagInundation なし・shelters 空)。

**交差判定の設計判断**: エッジ (2 次メッシュ内の短い道路区間) の両端点+中点をポリゴンに対してテストする近似方式にした。完全な線分-多角形交差判定 (Sutherland–Hodgman 等) は実装コストに対して、この用途 (エッジは短く、浸水域は広い連続領域) ではオーバースペックと判断。ポリゴン数が多くなる想定 (全国の A40 データ) に備え、ポリゴンごとの bbox 前置フィルタを Index に持たせている。

**動作確認**: 釜石メッシュ (584177, 8,397 ノード) に合成の浸水ポリゴンと避難場所 (圏外 1 件を含む) を与えて実行。8,729 エッジ中 1,381 エッジに FlagInundation が付与され、圏外の避難場所は shelters テーブルから正しく除外されることを確認した。

### 追記 (2026-07-20): 実データの取得元と全国投入

浸水想定区域・避難場所とも、実データの取得元を確認できたため取り込んだ (取得は WebSearch/WebFetch で公式配布ページを特定し、URL を推測せず確認してから行った)。

- **浸水想定区域**: 国土数値情報 津波浸水想定データ (A40)。都道府県別 Shapefile、44 都道府県分 (北関東・内陸県など沿岸を持たない県は対象外)、合計約 1.7GB。配布元: https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-A40-v2_1.html (各県 ZIP への実 URL はページの JS 内に埋め込まれており、`../data/A40/A40-XX/A40-XX_YY_GML.zip` 形式)
- **避難場所**: 国土地理院「指定緊急避難場所データ」の全国 GeoJSON (G空間情報センター配信、CC BY 4.0)。115,447 件中、「津波」列が該当する 40,393 件を採用 (FR-04)。配布元: https://www.geospatial.jp/ckan/dataset/hinanbasho

**ETL**: 実データは 1 都道府県あたり数万件の depth-band ポリゴンに分かれており、そのまま Index に載せるとファイルサイズ・メモリともに肥大化する (実測: 青森県のみで生ポリゴン 82,792 件・56MB)。このパイプラインはエッジが浸水想定区域に触れるかの boolean 判定にしか使わないため、`ogr2ogr` の `ST_Union` で都道府県ごとに 1 つの MultiPolygon へ dissolve し、`-simplify 0.00003度` (≈3m、エッジの端点+中点サンプリング近似の誤差予算内) で単純化してからマージした。結果、全国 44 都道府県で 808MB (dissolve 後も 387,395 個の非連結ポリゴン片、頂点数 946 万)。変換スクリプトは `pipeline/scripts/normalize-a40.sh` / `normalize-shelters.sh` としてリポジトリに残し、再現可能にしている (元データそのもの・変換後の GeoJSON は `pipeline/data/` 配下で gitignore 対象)。

**性能問題と対処**: 全国 Index (387,395 ポリゴン) をそのまま釜石メッシュ (8,729 エッジ) に適用したところ 3.49 秒かかった。エッジごとに 3 点 (両端点+中点) サンプルし、そのたびに全国の全ポリゴンの bbox を線形走査していたため。`Index.Subset(bbox)` を追加し、メッシュ処理の最初に全国 Index を対象メッシュ範囲へ 1 回だけ絞り込んでから edge ループに使うよう変更したところ、**3.49 秒 → 0.02 秒 (175 倍)** に改善した。全国 2,515 パッケージへの適用でも無視できるオーバーヘッドに収まる見込み。

**動作確認 (実データ)**: 釜石メッシュで 8,729 エッジ中 **4,022 エッジ (46%)** に浸水フラグが付与された。2011 年の津波で甚大な被害を受けた沿岸市街地であることと整合する。避難場所は 46 件(「鵜住居小学校・釜石東中学校校庭」等、実在の高台避難所)。

**ライセンス**: A40 は都道府県ごとに利用条件が異なり (大多数はオープンデータだが一部条件付き)、避難場所データは CC BY 4.0。[docs/licenses.md](../licenses.md) に記録した。全国パッケージを公開配布する場合は ADR-0002 (ライセンス未決) とあわせて都道府県別の利用条件を再確認すること。

## 帰結

- pipeline/cmd/build-package は「対象メッシュ列挙 → osmium 抽出 → グラフ構築 + DEM/浸水域焼き込み → region.sqlite + tiles.mbtiles + manifest 生成 → GCS」の構成になる
- 次の実装: **1 メッシュを end-to-end で生成する垂直スライス** (実在の沿岸メッシュ 1 個で region.sqlite を作り、サイズと生成時間を実測する) — 完了 (2026-07-18 の追記参照)
- app 側は GraphLoader (SQLite → 隣接リスト) と EvacuationRouter (A* + 動的コスト) をドメイン層 TDD で実装する — 完了 (2026-07-19 の追記参照)
- **未解決**: 浸水想定区域 (国土数値情報 A40) と指定緊急避難場所 (国土地理院) の実データ取得元。次セッションでユーザーに確認する
